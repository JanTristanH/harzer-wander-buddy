## Reihenfolge

1. Anbieterunterlagen und Auth0-Tenant prüfen.
2. Isoliertes Staging, Datenbankmigration, Backend-Secrets und Löschjob einrichten.
3. Die unten beschriebenen Tests auf Staging durchführen und Belege sichern.
4. Produktiv konfigurieren, Backend/Web-App veröffentlichen und öffentliche URLs prüfen.
5. Neue native Builds testen, Store-Angaben vervollständigen und separat freigeben.

Dieser Feature-PR richtet sich nach `develop`. Produktion wird nach dem vorhandenen Release-Verfahren über `main` veröffentlicht. Merge dieses PRs ersetzt weder Konfiguration noch Tests.

Prüfen, ob genau diese Standardbedingungen für das Konto gelten. Die [Support-Anleitung](https://support.auth0.com/center/s/article/how-to-obtain-a-copy-of-the-auth0-data-processing-addendum-dpa) bestätigt, dass der Okta-DPA auch Auth0 betrifft, belegt allein aber nicht die Annahme im eigenen Konto. Dann in IAM & Admin das Projekt wählen, „Cloud Data Processing Addendum → Review and Accept“ öffnen, lesen und annehmen. Annahmenachweis bzw. bestehende Einbeziehung sichern.

Gegen die Empfänger in `srv/legal-content.js` und Store-Angaben abgleichen.

## Checkliste: technische Einrichtung

- [ ] **Staging vorbereiten.** Separates Backend, separate Testdatenbank und geeigneter Test-Tenant. Zwei ausschließlich für diesen Test angelegte SSO-Konten A/B und ein separates Admin-Testkonto verwenden. Lokale Basic-Zugangsdaten aus AGENTS.md sind kein Store-Review-Konto und kein Auth0-Löschtest.
- [ ] **Auth0-Tenant prüfen.** Sicherstellen, dass das Löschen eines Auth0-Nutzers keine anderen Anwendungen beeinträchtigt. Nur dann `AUTH0_ACCOUNT_DELETION_MODE=dedicated-tenant` aktivieren. Bei gemeinsam genutzten Identitäten ist eine angepasste app-spezifische Entkopplung nötig; diese ist in diesem PR nicht implementiert.
- [ ] **M2M anlegen.** Auth0 Dashboard → Applications → Create Application → Machine to Machine. Auth0 Management API auswählen/authorisieren und nur `delete:users` freigeben. Client ID/Secret als Backend-Secrets speichern, niemals `EXPO_PUBLIC_*`. [API-Tokens](https://auth0.com/docs/secure/tokens/access-tokens/management-api-access-tokens), [Nutzerlöschung](https://auth0.com/docs/api/management/v2/users/delete-users-by-id).
- [ ] **Migration auf Staging testen.** Vorher einen geschützten Export/Sicherung nach Betriebsverfahren erstellen. `cd backend/hwb && npm run deploy:postgres` nur mit den richtigen Staging-DB-Secrets ausführen. Tabellen `AccountDeletions` einschließlich `lastAttemptAt`, `UserBlocks`, `ContentReports` und `ExternalUsers.contentRestricted` prüfen. `lastAttemptAt` darf bei bestehenden Aufträgen zunächst leer sein; der Worker verwendet dann `requestedAt` und setzt den Zeitstempel bei jedem Versuch. Bestehende Daten/Berechtigungen erhalten. Keine produktive Datenbank vom Laptop mit unkontrollierten Credentials migrieren.
- [ ] **Supabase-Zugriff neben CAP absichern.** In den Projekteinstellungen prüfen, ob die Data API aktiviert ist und welche Schemas/Rollen Zugriff haben. Die App nutzt Auth0 und CAP, keine Supabase-Auth-Policies; CAP-Annotationen schützen keine direkten PostgREST-Zugriffe. Interne Tabellen wie `AccountDeletions`, `ContentReports`, `ExternalUsers` und private Notizen nicht öffentlich freigeben. Wenn die Data API nicht verwendet wird, deaktivieren oder die App-Tabellen aus exponierten Schemas/Grants entfernen; andernfalls geeignete RLS-/View-/Grant-Regeln separat prüfen. Keine pauschalen `auth.uid()`-Policies für Auth0-Kennungen übernehmen. [Supabase: Data API absichern](https://supabase.com/docs/guides/api/securing-your-api).
- [ ] **Backend konfigurieren.** `CDS_ENV=production`, bestehende PostgreSQL-Verbindung, `ISSUER_BASE_URL` des tatsächlich benutzten Tenants, die zwei `AUTH0_MANAGEMENT_*` Secrets, Deletion-Modus und `LEGAL_TRANSFER_DETAILS` setzen. `MOBILE_CORS_ORIGINS` als kommaseparierte Web-Origin-Allowlist, z. B. `https://app.harzer-wander-buddy.de`; keine Pfade wie `/app/rnweb` und kein Wildcard-Origin. Bestehende SSO-Client-/Audience-/Session-Konfiguration erhalten.
- [ ] **Löschjob anlegen.** Dasselbe neue Backend-Image als Cloud Run **Job** in europe-west1 deployen. Startbefehl `node`, Argument `util/runAccountDeletionJob.js`, Arbeitsverzeichnis `/usr/src/app`; `start.sh` überschreiben. Gleiche bereits migrierte DB und M2M-Secrets wie der Webserver, `CDS_ENV=production`. Eine Aufgabe, z. B. Timeout 20 Minuten. Der Job führt keine DB-Migration durch. Runtime-Service-Account erhält nur die nötigen Secrets-/Datenbankrechte.
- [ ] **Scheduler einrichten.** Cloud Run Job → Triggers → Add Scheduler Trigger. Z. B. alle fünf Minuten (`*/5 * * * *`), Zeitzone Europe/Berlin. Dedizierter Scheduler-Service-Account mit `roles/run.invoker` nur auf diesem Job. Der Aufruf der Google Run API nutzt OAuth, keinen öffentlichen HTTP-Löschendpoint. [Offizielle Schritte](https://docs.cloud.google.com/run/docs/execute/jobs-on-schedule).

  Bei manueller Einrichtung in Cloud Scheduler: HTTP-Ziel `https://run.googleapis.com/v2/projects/PROJECT_ID/locations/europe-west1/jobs/JOB_NAME:run`, Methode `POST`, Body `{}`, `Content-Type: application/json`, OAuth mit dem dedizierten Scheduler-Service-Account und Scope `https://www.googleapis.com/auth/cloud-platform`. `PROJECT_ID` und `JOB_NAME` durch die eigenen Ressourcen ersetzen. Scheduler-Invoker und Job-Runtime sind getrennte Rollen: Der Invoker benötigt keine Auth0-Secrets, die Job-Runtime benötigt keine Scheduler-Verwaltungsrechte.
- [ ] **Ausführungen überwachen.** Job manuell einmal ausführen und erfolgreiche Ausführung prüfen. Danach Scheduler manuell auslösen und erneut die **Job-Ausführung** prüfen; erfolgreicher Scheduler-Dispatch alleine genügt nicht. Alarm auf fehlgeschlagene Jobs und überfällige Queue-Einträge einrichten; Namen/IDs/Token nicht in Alarmmeldungen veröffentlichen. Rückstau beachten: maximal 20 Löschungen pro Jobdurchlauf.
- [ ] **Bestätigung setzen.** Erst nach tatsächlichem Scheduler-/Retry-Test `ACCOUNT_DELETION_SCHEDULER_CONFIRMED=true` setzen. Danach mit den echten Konfigurationswerten `npm run check:legal-release --prefix backend/hwb` ausführen. Der Check ersetzt keine Prüfung des Vertragsinhalts, der IAM-Rechte oder des laufenden Jobs.
- [ ] **Produktionsmigration planen.** Nach Staging-Abnahme Migration/Deployment im bestehenden Release-Verfahren planen, zusätzliche Sicherung mit Löschfrist erstellen und Wiederherstellungsverfahren festlegen: gelöschte Konten dürfen nach Restore nicht wieder aufleben. Native App und Backend-API zusammen versionieren; alten Clients weiterhin erforderliche Backendfunktionen bereitstellen.

- [ ] **Admin-Moderation:** Nur Admin sieht Meldungen und kann Inhalte entfernen/Veröffentlichung einschränken. Vorher von B abgerufenes A-Bild nach Moderation oder A-Löschung erneut abrufen: HTTP 404, auch bei einer anderen Backend-Instanz. Normale Nutzer haben keinen Zugriff auf die Moderation.
